# Specification: 2048 clone, three themed prototypes

## 1. Product contract

This wish delivers three standalone, browser-playable 2048 games at the repo
root: `gothic/index.html`, `roman/index.html`, `modern/index.html`. Each is a
fully independent file tree — no shared JS/CSS/asset files, no cross-folder
references, no build step, no external network dependency (fonts, CDNs,
analytics, etc. must be inlined or self-hosted within the theme's own
folder). Opening any one `index.html` directly in a browser (via
`file://` or a static server) must be immediately playable.

All three implement identical game rules (section 3). Only presentation —
palette, typography, tile texture/border treatment, background, decorative
chrome — differs by theme. This wish does not include a landing/comparison
page, undo, animations beyond basic tile movement, difficulty variants,
leaderboards, account-based persistence, or a "continue past 2048" mode.

## 2. Resolved delivery decisions

| Area | Decision |
| --- | --- |
| File layout | One folder per theme at repo root: `gothic/`, `roman/`, `modern/`, each `index.html` self-contained. No shared engine or stylesheet. |
| Comparison page | None ships. The cook opens each file directly. |
| Win behavior | Reaching 2048 freezes the board (input stops) and shows a win message. No "keep going" mode. |
| Persistence | Each theme uses its own `localStorage` key(s), distinct from the other two, so playing one never affects another's saved state. |
| Grid/spawn odds | 4x4 grid; every spawn is 2 (90% probability) or 4 (10% probability) — identical across all three prototypes. |

## 3. Game behavior (identical across all three prototypes)

### 3.1 Board and spawning

- The board is a 4x4 grid of cells, each empty or holding a tile with a
  power-of-two value.
- A new game starts with exactly 2 tiles placed on random empty cells, each
  independently 2 (90%) or 4 (10%).
- After any move that changes the board (at least one tile slid or merged),
  exactly one new tile spawns on a random empty cell, with the same 2/4 odds.
- If a move produces no change to the board (no tile slid or merged in that
  direction), no new tile spawns and no move is recorded.

### 3.2 Moving and merging

- Four move directions: up, down, left, right, triggered by arrow keys or a
  touch swipe of that direction.
- On a move, every tile slides as far as possible in the chosen direction.
- Two adjacent tiles (after sliding) with equal values merge into one tile of
  double the value, once per tile per move — a merged tile does not merge
  again with a further tile in the same move (standard 2048 chain rule:
  scanning from the far edge inward, e.g. `[2,2,2,2]` moved left becomes
  `[4,4,0,0]`, not `[8,0,0,0]`).
- A merge adds the resulting tile's value to the score.
- Sliding/merging is computed per row or column independent of the other
  three.

### 3.3 Score

- Current score is visible at all times and starts at 0 for a new game.
- Best score is visible at all times, initialized from `localStorage` (0 if
  none stored), and updates whenever current score exceeds it.
- Best score persists independently of the current game: starting a new game
  or losing does not reduce or clear it.

### 3.4 Win condition

- The moment any tile reaches value 2048 (checked right after a move's
  merges resolve, including the spawn step), the game enters a won state:
  a visible win message appears, and further arrow-key/swipe input is
  ignored until the player restarts.
- Reaching 2048 does not end the ability to see the final board; it only
  freezes further input.

### 3.5 Loss condition

- After a move and its resulting spawn, if there is no empty cell **and** no
  two adjacent cells (horizontally or vertically) share a value anywhere on
  the board, the game enters a lost state: a visible loss message appears,
  and further arrow-key/swipe input is ignored until the player restarts.
- A board with any empty cell is never a loss, regardless of adjacency.

### 3.6 Restart

- A visible restart/new-game control is available at all times (including
  mid-game, in the won state, and in the lost state).
- Activating it clears the board, resets current score to 0, spawns 2 fresh
  tiles per section 3.1, clears won/lost state, and re-enables input. Best
  score is not reset.

### 3.7 Persistence

- On every board-changing move (and on reaching won/lost state), the current
  board, current score, and won/lost state are saved to `localStorage` under
  that theme's own key(s).
- On page load, if a saved game exists in `localStorage`, it is restored
  (board, score, won/lost state) instead of starting a new game. If none
  exists, or stored data is missing/corrupt, a new game starts.
- Best score is stored separately from the in-progress game state and is
  read/written independently (see 3.3).

### 3.8 Input

- Arrow keys (`ArrowUp`/`ArrowDown`/`ArrowLeft`/`ArrowRight`) trigger moves
  while the game is neither won nor lost.
- Touch swipes of sufficient distance in one of the four cardinal directions
  trigger the corresponding move under the same condition.
- Input while won, lost, or mid-restart-transition has no effect on the
  board.
- Arrow key presses do not scroll the page.

## 4. Acceptance criteria

For each of `gothic/`, `roman/`, `modern/`, delivery is complete when:

1. The file opens standalone (double-click or static serve) with no build
   step, no console errors, and no network request outside its own folder.
2. A fresh game shows a 4x4 board with exactly 2 tiles, score 0, and the
   stored best score (or 0 if none).
3. Each of the four arrow keys and the corresponding swipe gesture slides
   and merges tiles correctly per section 3.2, spawning a new tile only when
   the board changed, and updating the score.
4. A move that would change nothing (e.g. pressing a direction where every
   tile is already flush against that edge with no possible merge) leaves
   the board, score, and tile count unchanged.
5. Filling the board to a known no-move state (empty cells: 0, no adjacent
   equal pair) shows the loss message and blocks further input.
6. Reaching a 2048 tile shows the win message and blocks further input,
   without an automatic "continue" option.
7. The restart control returns to a fresh game (score 0, 2 tiles, won/lost
   cleared, input re-enabled) without clearing the best score.
8. Reloading the page mid-game (before winning/losing) restores the same
   board and score. Reloading after a win or loss restores that same
   won/lost state (not silently a fresh game).
9. Best score after a high-scoring game, followed by a loss and a restart,
   still reflects the earlier high score.
10. The three theme folders are visually distinct (palette/typography/tile
    treatment) and none references another theme's files, `localStorage`
    key(s), or assets.

## 5. Test seams

Each theme is a single HTML file, but the seams below should still be
identifiable for manual or scripted checks:

- **Pure move/merge function.** The row/column slide-and-merge logic for one
  direction (section 3.2) should be a plain JS function taking a board (or
  single row/column array) and returning the new array plus the score
  delta and a changed/unchanged flag — callable and testable in isolation
  from the DOM (e.g. via a `<script type="module">` opened in a JS console,
  or a small inline test harness), independent of rendering, spawning, or
  input handling.
- **Loss-detection function.** A plain JS function taking a board and
  returning true/false for "no legal move remains" (section 3.5), callable
  with a hand-constructed board array without needing to play a full game
  to reach that state.
- **Spawn function with injectable randomness.** Tile spawning (section 3.1)
  should accept or be steerable by a random source, so a test can force a
  specific empty cell and 2-vs-4 outcome rather than relying on real
  randomness — this is what makes deterministic win/loss/merge scenarios
  constructible.
- **DOM/state observability.** The rendered board, current score, best
  score, and win/loss message each have a stable, inspectable DOM location
  (e.g. a consistent id/class per tile cell and per status element), so a
  browser-automation check can read game state after simulating a key press
  or swipe without parsing pixels.
- **`localStorage` seam.** The save/load key(s) for board+score and for best
  score are identifiable and distinct per theme, so a test can seed, clear,
  or corrupt `localStorage` before load and observe the resulting behavior
  (resume vs. fresh game vs. graceful fallback on corrupt data).
- **Restart control.** A stable selector (id/class) on the restart button,
  so automation can trigger it directly rather than simulating a full loss.

Debug/test affordances beyond the above are not required; the seams are the
plain functions and stable selectors already implied by the acceptance
criteria, not a separate test-mode API.
