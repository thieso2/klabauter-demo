# Shaping map: 2048 clone, three themed prototypes

## What this wish is

Three standalone, plain-HTML/JS playable pages — Gothic, Roman, Modern — each a
complete 2048 game the cook can open directly in a browser and compare side by
side. The three share no code or assets; only visual direction differs. Scope
ends at delivering the three prototypes, not at picking a winner or building
whatever comes after.

Core mechanics, identical in all three:

- 4x4 grid; each spawn is a 2 (90%) or 4 (10%), the standard 2048 odds.
- Arrow-key and touch-swipe sliding/merging in four directions.
- Live score display, plus a best-score readout that survives a reload.
- Win at 2048: the board freezes — no further input is accepted, a message
  states the win (**q3**). No "keep going past 2048" mode.
- Loss when no legal move remains (no empty cell and no adjacent equal pair
  in any direction) — a message states the loss.
- A restart/new-game control, since a frozen win or lose state needs a way
  back in.

Themes differ only in the surface: palette, typography, tile texture/border
treatment, background, and any decorative chrome. Grid size, spawn odds,
scoring, and win/lose behavior do not vary by theme.

## What this wish is not

- Not a shared engine with theme skins on top — each prototype is a fully
  independent file tree (**q1**); duplication across the three is expected
  and fine.
- Not a multi-prototype landing/comparison page — deliver exactly three
  standalone pages, nothing that links or indexes them (**q2**).
- Not an endless/"keep going" variant of 2048 — winning stops the game.
- Not scoped to include undo, animations beyond basic tile movement,
  difficulty variants, leaderboards, or account-based persistence.
- Not responsible for picking a theme to carry forward — that's a follow-up
  wish, out of this one's scope.

## Decisions and rationale

**q1 — Fully independent files per prototype.** Each of the three lives in
its own self-contained tree with no shared JS/CSS/assets between them. This
keeps every prototype disposable and honest for comparison: the cook is
judging a real standalone artifact, not a shared core plus a stylesheet.
Chosen layout: one folder per theme at the repo root —
`gothic/index.html`, `roman/index.html`, `modern/index.html` — each folder
self-contained (inline or same-folder CSS/JS only, no cross-folder
references). This detail wasn't itself asked as a decision; it's the
natural implementation of "fully independent files."

**q2 — Three standalone pages only, no index.** No comparison/landing page
ships as part of this wish. The cook opens each of the three files directly.

**q3 — Win screen freezes the board.** Reaching 2048 shows a win message and
stops accepting input; there's no "continue past 2048" mode to build or
maintain across three prototypes.

**q4 — Persist via localStorage.** Interpreted as the standard 2048
behavior: current board + live score persist so a reload resumes the same
game in progress, and best score persists independently of the current
game (a fresh loss/restart doesn't erase it). Since the three prototypes
are fully independent (q1), each uses its own localStorage key(s) — no
shared storage namespace, so playing one theme never clobbers another's
saved game or best score. This scope wasn't spelled out in the answer, but
it's the conventional meaning of "persist via localStorage" for this game
and doesn't create a second decision fork worth a round-trip.

## Good outcome and acceptance criteria

A good outcome is three files the cook can each open by double-clicking (or
serving statically) and immediately play to a win or a loss, with visibly
distinct art direction and identical underlying rules. Delivery is complete
when, for each of `gothic/`, `roman/`, `modern/`:

- The page loads with no build step, no external network dependency, and no
  console errors.
- Arrow keys and touch swipes slide/merge tiles correctly in all four
  directions; score updates accordingly.
- Reaching 2048 freezes the board and shows a win state; running out of
  moves shows a loss state; both are recoverable via a restart control.
- Reloading mid-game resumes the same board, score, and best score from
  localStorage; the three prototypes' saved state never interferes with
  each other.
- The file tree for that prototype has no reference to the other two
  prototypes' files.
